# Grype Vulnerability Scanning Documentation & Sample Reports

This directory contains technical documentation and validated sample scan reports for the [Anchore Grype](https://github.com/anchore/grype) content-based vulnerability scanner integrated into the Eclipse Temurin Linux packaging pipeline (`linux_new`).

---

## 1. What the Grype Scanning Process Does

When Linux installer packages (`.apk`, `.deb`, `.rpm`) are built, Grype extracts each package archive and inspects the **installed file system contents** that are delivered to end users.

### Cataloguers Executed
Grype executes three specialized cataloguers against the unpacked package directory:

1. **`java-jvm-cataloger`**:
   - Locates and parses the bundled `release` file inside the JDK/JRE root directory:
     ```properties
     IMPLEMENTOR="Eclipse Adoptium"
     JAVA_VERSION="25.0.4.1"
     ```
   - Derives the canonical Common Platform Enumeration (CPE):
     ```
     cpe:2.3:a:oracle:openjdk:25.0.4.1:*:*:*:*:*:*:*
     ```
   - Matches this CPE against the National Vulnerability Database (NVD) and Oracle Critical Patch Update (CPU) advisory feeds.
2. **`java-archive-cataloger`**:
   - Inspects bundled Java archives (such as `jrt-fs.jar` and extension JARs) using SHA-1 fingerprints and Maven coordinates matched against the GitHub Advisory Database.
3. **`binary-classifier-cataloger`**:
   - Fingerprints compiled native ELF binaries (e.g., the `java` launcher).

---

## 2. Scan Scope & Boundaries

* **In Scope**:
  - The installed files that actually ship within the Temurin package (the Java runtime image, binaries, internal libraries, and bundled JARs).
* **Out of Scope**:
  - Distro base runtime dependencies declared in package prerequisites (e.g. `glibc`, `musl`, `alsa-lib`, `libX11`, `zlib`). These are managed by the host operating system's package manager.
  - Source RPMs (`.src.rpm`), which contain only spec files and source tarballs.
* **Why Content Scanning (CPE) Is Used Instead of PURL**:
  - Package URL (PURL) lookups (`pkg:deb/...`, `pkg:rpm/...`, `pkg:apk/...`) query distro-specific repository feeds for packages managed by the Linux distribution.
  - Because Temurin packages are privately built and not tracked in upstream distro feeds (e.g. Ubuntu main or Alpine community), PURL lookups return zero matches. Content-based CPE scanning against NVD and Oracle CPU feeds provides accurate vulnerability detection.

### What the Sample Reports Show
* **Clean Bill of Health**: All 15 scanned package artifacts pass with 0 CVE findings at or above the `HIGH` threshold.
* **Release Fix Verification**: The scanned version (`25.0.4.1`) is above all known historical OpenJDK vulnerability thresholds in NVD and Oracle CPU advisories (including recent CPU fixes such as CVE-2026-61308 and CVE-2026-70907).

* **Headless Equivalence**: Full JRE and headless JRE contain identical JVM binaries, producing identical vulnerability profiles.

## 4. Generated Report Artifacts

During each scan run, the following report files are produced in the configured output directory (`build/grype-results-<dist>/`):

1. **`<package-stem>.json`**: Full canonical Grype v6 JSON report containing the execution descriptor (scanner version, DB build timestamp, schema version, and configuration snapshot).
2. **`<package-stem>.sarif.json`**: Static Analysis Results Interchange Format (SARIF v2.1.0) report for ingestion into GitHub Code Scanning or security dashboards.
3. **`<package-stem>.txt`**: Human-readable sorted text table.
4. **`summary.md`**: Markdown summary table generated by [`grype-summary-report.py`](../grype-summary-report.py) for CI step summaries (`$GITHUB_STEP_SUMMARY`) and PR reviews.
5. **`summary.txt`**: Consolidated plain-text summary matrix.

## 5. Exit Codes & CI Gate Behavior

The scan scripts exit with the following codes:

* **`0` (PASSED)**: No vulnerabilities detected at or above the `--fail-on` threshold (default: `high`).
* **`1` (ERROR)**: Script execution failure (e.g., missing package files, archive extraction error, or database schema mismatch).
* **`2` (POLICY BREACH)**: One or more unsuppressed vulnerabilities found at or above the configured severity threshold.

In the Jenkins pipeline ([`linux_new/Jenkinsfile`](../../Jenkinsfile)), scanning runs in an **informational / non-blocking mode**: exit code `2` logs a warning and marks the Jenkins build stage as `UNSTABLE`, allowing package archiving and downstream publishing to proceed.
